# The corpus census, without the big bang

The design for PRIORITIES item 1 (agreed, Steve + Claude, 2026-08-19). This
directory holds the census artifacts: per-program IR and emitted zig
(gitignored, regenerated by `corpus_run.py` at the repo root), the stage
outputs (`transpile.json`, `run.jsonl`), and -- once the plumbing below
lands -- `census.json`, the banked verdict set.

## What the project is for

Four objectives hide under "corpus conformance", and they want different
machinery:

1. **The census** -- rank missing emitter arms by how often they bite across
   553 real programs. Ranking needs breadth, once.
2. **The conformance gate** -- programs that transpile clean must run and
   match `.expected`. A standing property, not a one-shot.
3. **Regression detection** -- an emitter change must not silently break a
   program that matched yesterday. Nothing provides this today; a fix is
   verified by rerunning everything or by hope.
4. **Refusal reproduction** (`.failing`) -- later, a different question.

## Where the time actually goes (measured 2026-08-19)

The stage split is the whole story:

    .codex -> IR    (native codexir)   ~0.15s/prog, depends on the SEED only
    IR -> .zig      (native zigemit)   ~0.4s/prog, depends on the EMITTER
    zig run          per program        ~1-3s typical, 300s cap -- THE cost center

So a full census is roughly: emit all 553 in ~4 minutes, run the ~280
transpile-clean ones in ~10-20 minutes. **The big bang was never actually
expensive in wall time -- it is a coffee-break job.** The pain was
elsewhere: hosted `codexir` aborting (80 of 553, one known cause being
`text-to-double-bits` as an unimplemented prelude marker, so ANY real
literal aborts the native front end), hangs that used to take the VM with
them (now capped), and the wholesale character of the thing -- every run
re-answers 553 questions to learn about one change.

## The two structural facts that make incrementality free

**Everything is deterministic and content-addressable.** A program's
verdict is a pure function of (its emitted `.zig`) x (zig toolchain). The
`.zig` is a pure function of (its IR) x (emitter). The IR is a pure
function of (resolved source) x (seed). All the intermediates are already
files in this directory.

**Re-emitting is 30x cheaper than re-running.** After an emitter change,
regenerate all 553 `.zig` (~4 min, native) and hash them: **only programs
whose `.zig` changed can change verdict.** A one-arm emitter fix touches
the programs that use that arm -- usually a handful -- so the expensive
stage shrinks to exactly the affected set. The one sour note: the prelude
is embedded in every emitted file, so a prelude edit changes every hash
and honestly costs a full rerun. Accept that in v1; most emitter changes
are arm changes. (A v2 could hash the program section separately and grep
which programs reference a changed `cx_*` fn -- cheap and sound enough --
but that is optimization to do when a real prelude-heavy week hurts.)

## The design

**1. Bank the census, diff it like a truth file.** `census.json`
(name -> verdict + marker list + zig-hash), tracked, rewritten only by a
deliberate banking step. Day to day, the interesting output is the DIFF
against the bank: which programs flipped match->differ (regression),
differ->match (a fix landed), refused->match. This is the banked-
diagnostics philosophy (PRIORITIES item 8) applied here, and it converts
"278/117/95/33/5" -- a wholesale number nobody can act on -- into a short
list of names.

**2. Changed-only reruns.** `corpus_run.py --changed`: re-emit all,
compare hashes to the bank, run only the changed set, report the verdict
diff. The cache key includes the zig version and the native-tool
fingerprint, so a toolchain or Update bump can never serve a stale
verdict. This is the everyday loop: emitter fix -> native rebuild
(~1 min) -> `--changed` (~5 min typical) -> a diff naming exactly what
moved.

**3. A sentinel set, chosen by the data instead of by hand.** We hold the
IR of every program, and the emitter's surface is finite (~67
builtin-emitter arms, 24 IRExpr ctors, ~40 binops, 265 builtin rows).
Greedy set-cover over "which arms does each program's IR exercise" yields
a minimal subset -- plausibly 30-60 programs -- that touches every arm
any corpus program touches. That is the fast gate: ~1-2 minutes, run on
every emitter change even when `--changed` says nothing moved (it catches
prelude-behavior changes the hash trick cannot see cheaply). The cover is
recomputed per-Update from the fresh IRs, so it cannot rot.

**4. Full census stays, but scheduled, not habitual.** Per-Update (the
IRs regenerate anyway, since the front end moved) and before filing any
breadth claim upstream. It is a banked, ~20-minute away-work job -- the
tonight.sh slot -- not the default keystroke.

## Sequencing

1. **Unblock before measuring more.** DONE 2026-08-19: the real-literal
   abort (`text-to-double-bits`) and multi-byte CCE were one family and
   poisoned the denominator (80 codexir SIGABRTs and a slice of the 95
   refusals); both landed on the pin the same day.
2. **Plumb the bank + `--changed`** (an afternoon of keyboard work, no
   compute): the `census.json` schema, hash comparison, verdict-diff
   output.
3. **Run ONE full census as the baseline bank.** Away work, ~20 min.
4. **Extract the sentinel set from that run's IRs** and wire it as the
   default quick gate.

After that the big bang retires to its two legitimate occasions, and the
daily loop is minutes.

## Deliberately not built

- **Parallel runners.** One compute job at a time is the law of this
  machine, and serial changed-only runs are already minutes.
- **A database.** Files and one json, like everything else here.
- **The prelude-diff cleverness** (v2 above) until a prelude-heavy week
  actually hurts.
- **Any silent skip.** `--changed` must print what it did NOT run and why
  ("512 unchanged since bank 2026-08-19"), or an unchanged-but-broken
  assumption reads as green. The sentinel gate exists partly as the
  cross-check on the hash shortcut.
